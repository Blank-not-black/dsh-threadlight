# 开发方向

Threadlight 面向通过 DSH 开发软件、主要用用户操作和预期结果来描述需求的人。开发中的项目从确认方向进入具体实现，已有项目从看懂当前行为进入下一轮开发。两种入口围绕同一套功能区、线路和步骤展开。

## 两种工作方式

**See how it works｜看懂已有项目**

从当前代码和测试梳理用户能做什么、操作会怎样继续、失败时会发生什么。沿图可以查看实现依据、测试位置和待核实的步骤。读者可以从已理解的线路提出下一项改动。

**Shape what comes next｜决定接下来怎么做**

在从零开发或新增功能时，Threadlight 引导用户先确认目标用户、要完成的事情、首版范围和成功条件。用一条可走通的用户流程表明入口、可见结果和关键失败分支。方向确认后，把该线路、待实现步骤和验收条件交给 DSH 作为实现上下文。

实现完成后，对照已确认的线路回挂代码、测试位置和实际验证结果，显示实现过程中发现的差异和仍待确认的行为。已确认的预期随版本保留，后续的阅读和改动都能追溯当初的决定。界面应让用户看得出哪些步骤仍是计划、哪些有实现依据、哪些已经实际验证。

## 在图上编辑并交给 DSH

- **批注表达预期**。用户可以在步骤或分支上用自己的话描述问题、预期结果和原因。批注记录对应的线路、步骤或分支及其版本。
- **编辑流程草稿**。用户可以新建线路，也可以从已有线路建立草稿。在草稿中可新增、改写或移除步骤，连出下一步，并为分支写明触发条件和用户看到的结果。箭头决定执行顺序，布局由查看器生成。已有实现图谱保留原快照，便于对照用户想改的地方。
- **提交给 DSH**。用户提交选中的批注和草稿变更后，Threadlight 自动生成实现提示词并交给对应项目的 DSH 会话。任务包含用户原话、改动范围、关联步骤、预期行为、验收条件和可用证据。提交记录保留草稿版本和对应任务。
- **回到图上复核**。DSH 返回的实现位置和实际验证结果挂到对应的步骤或分支。用户可以在原位置查看实现与预期的差异，并继续修改草稿或补充批注。

## 当前底座

Threadlight 将 Git 工作树的可分析文本交给专用 DSH 文档会话。首次生成全量图谱。下一次处理源码变动时带上上次图谱、变更文件和受影响线路，只合入文档补丁。Node 校验器检查图谱结构和源码引用，离线 HTML 和分模块 Markdown 共用同一个快照。

查看器提供三个入口。功能总览从项目向下逐级展开领域、功能区、线路和步骤。操作流程展示线路内部的步骤、分支和源码证据，并可按图谱记录逐步导览。功能关系从当前线路出发，用实线箭头表示接续，用虚线箭头表示使用。Obsidian 导出保留为可选分发入口。

DSH 中的开场页左侧 **See** 用于创建工作区，右侧 **Shape** 用于查找并打开已有工作区。已有图谱的工作区打开图谱，尚未发布图谱的工作区打开流程草稿。

DSH Web 支持功能区批注，以及新建或复制线路草稿。用户可以编辑步骤与分支、写批注并选择随任务提交的内容。提交指定版本后，Threadlight 在对应工作区新建会话并发送实现提示词。

宿主内的会话控件也在向 DSH 原生插槽收拢：会话顶栏按钮、输入框下方的项目状态胶囊，以及 `threadlight_graph` / `threadlight_annotate` / `threadlight_export` 三个工具的对话卡片，都注册在宿主的槽位里，而不是 iframe。批注箱支持按模块选择 agent preset 并并行提交，每个模块一个会话、独立回执；首页、工作区列表和批注箱本身仍是插件自己的页面。

## 技术选型

拓扑绘制、自动布局、图编辑和界面组件可以复用成熟的第三方库，减少通用能力的重复开发。具体选型按图形交互和界面需求决定。

## DSH 适配层

已经完成：会话顶栏入口、输入框下方的项目状态胶囊、三个工具的对话卡片、批注箱的按模块并行提交与 agent preset 选择。接下来：

- **迁移自有页面**。首页、工作区列表、批注箱改为宿主插槽里的 React 组件，去掉对应的 iframe；离线查看器要保持单文件自包含，最后再迁移。
- **减少轮询**。用会话投影和宿主状态驱动侧栏徽标与会话内状态，替换页面里的定时刷新。
- **插件设置**。提供设置命名空间，保存默认模型、CLI 路径、代码索引、默认 agent preset 和默认图谱深度。

## 接下来

1. **完成一次实现回流**。把 DSH 返回的实现和验证依据挂回对应步骤。用户从已有线路建立下一版草稿，可以就具体分支继续修改和提交。
2. **对照预期和实现**。对比已确认的计划、实际实现和相邻实现快照。按线路显示何处符合预期、何处发生变化、哪些行为还需要检查。

用同一条流程检验两种工作方式。用户能在实现前在图上定义一个失败场景，并通过提交发起 DSH 任务。另一位不了解代码的用户在交付后能沿图找到该行为，并判断它有实现依据、已经实际验证，还是仍待核实。
